# 0014 — Settings navigation nesting: rail children vs Disclosure sections vs tabs

**Date:** 2026-09-06 · **Question:** should Settings sub-sections (General / Dock / Companion / Backup) live as nested children under the app-rail "Settings" item (indented below Settings in the left NavRail), vs Disclosure sections on the one `/settings` page, vs top tabs / side-rail pages? The user's idea is nested items below Settings in the app nav; the worry is long titles + readability + nested-rail confusion.

## Sprout ground truth (measured, not inferred)

- Rail is **200 px fixed, non-resizable**: `.rail { width: 200px; flex-shrink: 0; … padding: var(--space-5) var(--space-3) var(--space-4); }` (`src/lib/components/NavRail.svelte:122-130`). The shell is a flex row with one scroll container (`.shell` / `.stage` / `.main`) and the document never scrolls (`src/routes/+layout.svelte:116-133`, `98-109`).
- Rail has **no headings, three frequency-split clusters separated by hairline dividers**: `clusters` comment cites research 0004 ("daily quick surfaces first, setup next, reference last — clusters separated by hairline dividers, no headings", `NavRail.svelte:9-31`); dividers are `height: 1px; background: var(--border)` (`NavRail.svelte:159-163`). Settings sits last in the reference cluster (`NavRail.svelte:26-30`).
- Rail items are **uppercase mono micro-labels with no truncation handling today**: `.rail__item` is `font-mono, text-xs (11 px), tracking-mono 0.06em, uppercase` with `padding: 7px var(--space-3)` (`NavRail.svelte:165-180`); `.rail__label` is a bare span with no `overflow`/`text-overflow`/`white-space` rule (`NavRail.svelte:77`). Active = `accent-tint` bg + `accent` text + `aria-current="page"` on exact-path match (`NavRail.svelte:71-76,187-190`).
- Settings page is **one `/settings` route, `PageHeader` chrome (0005), `max-width: 680px`, Disclosure-grouped**: `PageHeader title="Settings"` (`src/routes/settings/+page.svelte:905-910`); `.settings { max-width: 680px; margin: 0 auto; }` (`+page.svelte:1610-1613`); three labeled `Disclosure` states — `companionOpen` ("Companion"), `advancedOpen` ("Reveal tuning", dock-conditional), `housekeepingAdvancedOpen` ("Advanced") (`+page.svelte:98-100,1175-1180,1248-1253,1409-1414`). Per-monitor knobs flatten into reused `.knob` rows, "no nested card" (`+page.svelte:1102`). The dirty bar is pinned `left: 200px` — i.e. it assumes the 200 px rail (`+page.svelte:1626-1629`).
- **Truncation/wrap constraint (explicit):** rail padding is `--space-3: 12px` each side (`src/lib/styles/tokens.css:81-84`), item padding is another `var(--space-3)` each side — so a top-level label gets ~`200 − 24 − 24 = ~152 px`. A nested child indented one step (OS indent precedent is ~16–20 px; Telerik `HierarchyIndent` default 20 documents the scale — see OS sources below) keeps **~132 px**. At 11 px uppercase JetBrains Mono + 0.06 em tracking, that fits roughly one short word plus a second clipped word: labels like "Backup & housekeeping" (20 chars) or "Quick Launch dock" (17 chars) **cannot fit on one line and would ellipsis-truncate**; wrapping to two lines would break the rail's single-row rhythm and collide with the uppercase micro-type. Any nested child therefore needs the 0004:4 analogue — short label + `ellipsis + title tooltip + aria-label` (0004 rule 4: "labels of 1–3 words… icons require tooltip + `aria-label`", `docs/research/0004-progressive-disclosure-and-clips.md:28-32`). In-repo ellipsis precedent already exists (`overflow: hidden; text-overflow: ellipsis; white-space: nowrap` in `GroupAccordion.svelte:92-94`, `ProductFormDialog.svelte:591-593`, `PresetPacket.svelte:98-100`).
- Disclosure anatomy precedent (0006:9): caret-in-margin, content at title level; Sprout's shared `Disclosure` is the filled triangle right→down, labeled mode is a flat full-width header row (`src/lib/components/Disclosure.svelte:4-11,75-86`; `docs/research/0006-notion-design-patterns.md:84-88`).

## Findings

1. **Notion keeps Settings sub-navigation inside the Settings modal sidebar — never as app-rail children.** All account changes route `Settings → {your name}` / `Settings → Preferences`; all workspace changes route `Settings → People/Members`, `Settings → Security`, etc. (account-settings + members sources above). The app sidebar and the Settings sidebar are two separate navigations: the app sidebar nests *content* (Teamspaces → nested pages via toggles), while Settings nests *concerns* (section → tab). This extends 0006:8 (only account/global concerns centralize in Settings) and 0006:4 (per-object controls stay at the object).
2. **Notion avoids the truncation problem by construction: sidebar labels are 1–2 short words.** Observed label set across the cited help paths: Preferences, Notifications, Connections, General, People, Members, Guests, Security, Billing, Sites, Emoji, Calendar accounts — never a sentence-length label. Notion Help documents no truncation behavior for Settings labels; the method is short labels, not ellipsis engineering. Live-behavior note (first-hand pattern, corroborated by SaaSUI Notion-Settings screenshots cited in 0006 sources): the Settings modal sidebar is wider than a 200 px app rail, items are single-line, and a top search filters the sidebar — search, not nesting depth, is the escape hatch.
3. **Discord's User Settings is a modal with a grouped left sidebar; nesting bottoms out at section → inner-tab, and children exist only while the modal is open.** Desktop opens via the bottom-left cogwheel into User Settings with a left sidebar; mobile groups the same items under an explicit **App Settings** header (Voice guide source). Long-form areas nest one more level *inside* the right pane, not as deeper sidebar children: **Voice & Video → Voice / Video / Debugging tabs**, Video tab → **Advanced** section; **Data & Privacy → Profile Privacy** section. The sidebar never leaks into the app's server/channel navigation — closing the modal removes the entire sub-navigation. Labels stay 1–3 short words (My Account, Profiles, Appearance, Accessibility, Voice & Video, Notifications, Data & Privacy); no wrapping/truncation handling is documented because none is needed.
4. **VS Code scales the same idea: groups in a tree + search that filters to matches + modified markers — hierarchy without pages.** Groups ("Commonly Used" first, then per-feature groups, then Extensions) are navigated via the left tree; selecting a group focuses/scrolls the right pane (settings-groups source). Search "filters the settings to only show those that match"; `@`-filters scope by extension/feature/id/language/tag/modified; modified settings carry a colored left bar; the gear menu offers Reset/Copy ID/Copy as JSON (settings-editor source). Sub-groups indent under parents in the tree; filtering collapses the tree to matches rather than opening new routes. There are no per-group URLs-as-pages for most groups — the tree *is* the navigation.
5. **OS guidance converges: two levels max, indent children, keep the ancestor selected, keep labels succinct, ellipsis + tooltip when space runs out.** WinUI: two levels ideal; selection indicator on the left edge in left mode; a selected child in a collapsed subtree shows its first visible ancestor as selected (NavigationView source). Apple: max two sidebar levels, group with disclosure controls, succinct labels minus filler words (Sidebars source). Microsoft's flat-vs-hierarchical cut is ~7–8 peer pages (Navigation-basics source) — below that, peers stay flat. For overflow text the platform primitive is ellipsis (`CharacterEllipsis`/`WordEllipsis`, Text-Trimming source) paired with the standing recommendation to add a tooltip for trimmed text (microsoft-ui-xaml #170).
6. **Nested-rail children have three concrete costs in Sprout's rail that none of the precedents pay.** (a) *Width*: ~132 px usable after indent (measured above) forces ellipsis on exactly the proposed long labels. (b) *Grammar collision*: the rail's organizing principle is frequency-split clusters with no headings (NavRail.svelte:9-11); indenting four Settings children under one parent introduces a second organizing principle (hierarchy) inside a surface whose users learned clusters — cf. 0006:5 (relocating familiar controls has a real cost). (c) *State interaction*: the rail already owns exact-match `aria-current="page"` plus a dirty-guard intercept on Settings (ticket 116, `beforeNavigate` in `+page.svelte:266-277`); per-child routes (`/settings/dock` etc.) would multiply guard/dirty-barhairline cases and the `left: 200px` dirty-bar assumption for zero wayfinding gain at four sections.

## Rules for Sprout

1. **Settings sub-navigation lives inside `/settings`, never in the app rail — until the graduation threshold (rule 5).** Follows Notion (finding 1), Discord (finding 3), VS Code (finding 4), 0006:8. The rail keeps its flat frequency-split clusters; Settings stays one rail item.
2. **Disclosure sections over page splits at current scale.** Four sub-sections on a `max-width: 680px` page with three existing Disclosures is exactly 0006:7 territory ("keep long layouts scannable without fragmenting into new pages"). No top tabs (0004:4 reserves tabs for peer surfaces with 2–7 short labels, and Settings sub-sections are not peer app surfaces) and no side-rail sub-pages.
3. **Label-length rule (binding).** Rail labels: ≤3 words, ≤~18 characters at current type (0004:4 analogue); if a future rail child would ellipsis at 132 px, shorten the label instead of engineering wrapping — per Apple "omit unnecessary words" and Notion finding 2. Concrete renames if children ever graduate: "General", "Dock", "Companion", "Backup" (all 1 word) — never "Backup & housekeeping" / "Quick Launch dock" in the rail. Disclosure labels on the page may stay descriptive ("Reveal tuning", not a second "Advanced" — existing 0008-rule-3 scent precedent in `+page.svelte:1240-1246`); the current triple ("Companion" / "Reveal tuning" / "Advanced") should resolve the duplicate-generic risk by renaming the last to "Housekeeping" when next touched.
4. **Active-state + truncation contract for any future nested child (binding if built).** Children render only while the parent route is active (`/settings*`); the active child gets `aria-current="page"` and the accent-tint treatment, and the parent "Settings" simultaneously shows the ancestor-selected state (Microsoft "first visible ancestor will show as selected" precedent) so a collapsed/away state never strands orientation. Indent exactly one step (~16 px, hierarchy-indent scale); single-line `ellipsis + title tooltip + aria-label` per the in-repo precedent and the platform tooltip-when-trimmed guidance — never wrap to two lines in the rail.
5. **Graduation threshold (when to leave Disclosures).** Graduate from Disclosure sections to nested children (settings-local sub-nav first, rail children last) only when **any** holds: (a) ≥7 sub-sections (Microsoft >7 hierarchical cut); (b) deep-linking/search demand (a support path needs `…/settings#dock` or a filter box because users can't find knobs — the VS Code trigger); (c) a sub-section grows its own configuration surface (0006:1 — e.g. Companion already points URL authoring at `/companion` via "Manage sites" rather than duplicating it). Until then, adding a fourth Disclosure ("Backup & housekeeping" grouping Export/Restore/retention-adjacent knobs) is cheaper than any navigation change.
6. **Search before hierarchy.** If Settings outgrows scanability, add a settings-local filter (VS Code precedent: filter-to-matches, `@modified`-style scoping is future work) before adding navigation depth. Search scales to long labels; nesting punishes them.

## Verdict

**Hybrid, in this order: keep Disclosure sections on the one `/settings` page now; do not add nested rail children, top tabs, or side-rail pages.**

- *Now:* keep `Companion` / `Reveal tuning` / housekeeping Disclosures; group Backup-adjacent knobs under one Disclosure if the page grows; rename the generic "Advanced" Disclosure to "Housekeeping" for scent (0008 rule 3) when next touched. No application-code change in this note.
- *If/when rule 5 fires:* build a **settings-local** sub-nav (anchor list or left sub-rail inside the 680 px page, VS Code-tree grammar) first; promote to **nested rail children** only if deep routes (`/settings/dock`…) prove necessary — and then only with 1-word labels (rule 3) and the active-state/truncation contract (rule 4): children visible solely under `/settings*`, parent holds ancestor-selected styling, one indent step, single-line ellipsis with `title` + `aria-label`, no wrapping.
- *Why not the user's nested-rail idea today:* at four sections the precedents are unanimous — Notion, Discord, and VS Code all nest Settings concerns *inside* the Settings surface, and both OS guides cap sidebar hierarchy at two levels with short labels. In Sprout's 200 px uppercase-mono rail the four proposed children buy no wayfinding (the whole page already fits one scroll) while paying width (ellipsis on the exact long labels proposed), grammar (hierarchy inside a cluster-organized rail), and state (guard/dirty-bar × N routes) costs documented in finding 6.
